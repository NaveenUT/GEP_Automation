- **Step:** Step 9: Choose the payment method and enter the PO number (`tests/orders/GEP_Orders.spec.ts:158`, via `GepCheckoutFlow.fillShippingAndBilling` → `GepShippingBillingPage.selectImmediateScheduleIfShown`, `src/flows/GepCheckoutFlow.ts:44`, `src/pages/GepShippingBillingPage.ts:129-133`)
- **Page object / getter:** `GepShippingBillingPage.immediateScheduleRadio` (`src/pages/GepShippingBillingPage.ts:26-29`)
- **Error:** `locator.check` — strict mode violation: `locator('input[type="radio"][value="IMMEDIATE"]')` resolved to 2 elements.
- **Old locator:** `this.page.locator('input[type="radio"][value="IMMEDIATE"]')`
- **New locator:** `this.page.locator('input[type="radio"][value="IMMEDIATE"]').first()`
- **Why:** The saved page snapshot (`test-results/orders-GEP_Orders-GEP-Orde-e0174-rder-placesOrder-regression-us-qa/error-context.md`) shows the reordered cart split into two "Shipped From ..." sections on Shipping & Billing — "Shipped From Henry Schein Warehouse" (own inventory) and "Shipped From Big Desk Drawer" (marketplace partner) — each with its own "Shipping & Scheduling" radio group. The strict-mode error itself names both matches: `getByRole('radio').first()` (Henry Schein Warehouse group, listed first in DOM/page order) and `locator('section').filter({ hasText: 'Shipped From Big Desk Drawer' }).getByRole('radio')`. Only the Henry Schein Warehouse group offers Immediate/Delayed/Recurring alternatives (group `ref=e399` has 3 radios); the Big Desk Drawer (partner) group only ever renders a single, already-checked "Immediate" radio with no Delayed/Recurring alternative (group `ref=e482` has 1 radio) — it is not a group this "reset to Immediate" check needs to act on. Scoping to `.first()` restores the getter to matching exactly the one radio the method's intent (reset an account's remembered Delayed/Recurring choice back to Immediate) applies to, without changing `selectImmediateScheduleIfShown()` or the flow that calls it. No `data-test-id` exists on this input (confirmed via `error-context.md` and by grepping `src/` for the scheduling radios — the sibling `recurringScheduleRadio` getter is CSS-attribute-based too, for the same reason), so a CSS attribute selector remains the best available option per the resilience preference order; `.first()` disambiguates it deterministically by DOM order rather than switching selector strategy.
- **Confidence:** medium-high — the fix is deterministic and matches the method's original single-radio intent; not "high" only because DOM order (own-warehouse section before marketplace-partner sections) is inferred from this one snapshot rather than confirmed as a guaranteed invariant across all multi-vendor cart layouts.
